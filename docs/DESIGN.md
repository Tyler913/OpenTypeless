# Design

## Goal

Hold a key, speak for anywhere from two seconds to several minutes, and get the text you would have typed, inserted at the cursor. Long dictation has to be as reliable as short dictation. That is the main reason this project exists.

Out of scope: voice Q&A, accounts and sync. (Translation and rewriting selected text came later, as opt-in modes on a chord: see below.)

This document describes the macOS app; file names below are under `macos/Sources/`. The Windows app follows the same design with Windows APIs. [WINDOWS-PORT.md](WINDOWS-PORT.md) maps each file and system API to its Windows counterpart.

## Why other tools fail on long dictation

From reading several open-source voice-typing apps and the provider documentation:

1. **One request per recording.** The full recording is uploaded as a single speech-to-text request. OpenRouter documents that "upstream providers time out after 60 seconds per request" and recommends splitting long recordings. A longer client-side timeout doesn't help.
2. **Total timeouts on streaming calls.** One app gives the clean-up request a 30 s timeout that includes streaming the response body, so long outputs are killed mid-stream.
3. **All-or-nothing.** Any failure discards the recording.
4. **Connection drops under concurrency.** Real runs against OpenRouter showed `NSURLErrorNetworkConnectionLost` (-1005) when the server rejects a request mid-upload and shared connections are dropped. Treating it as retryable fixes it.

## Pipeline

```
key down ─► warm the provider connections
mic ─► AVAudioEngine ─► 16 kHz mono PCM ─┬─► WAV file on disk (written continuously)
                                         └─► Chunker + pause tracker
                                               │ at the first pause once 8 s are pending (else by 28 s, at the quietest 0.4 s window): cut
                                               │ at every pause: transcribe the pending audio ahead of time
                                               ▼
                                         STT queue (≤3 concurrent, per-chunk retries, silence trimmed)
                                               │ speculative tail done ─► start the clean-up ahead of time
release key ─► last chunk (often already transcribed) ─► join in order ─► clean-up LLM (streaming) ─► paste / clipboard
                                                                                │ on failure            │
                                                                                └─► insert raw transcript └─► then save costs and History
```

### Chunker (`TypelessCore/Chunker.swift`)
- **At a pause, once 8 s are pending.** As soon as the speaker has been quiet for 0.3 s after speaking (the speculative tail's pause, judged on 30 ms frames like `PauseTracker`), the chunk is cut in the middle of those 0.3 s and sent while they go on. The wait for a chunk grows with its length (about 0.05 s per second of audio for one-chunk dictations in 789 timed sessions, more than the latency model's 0.02 s), so a dictation that pauses now and then has at most about 8 s, plus what follows its last pause, left to send at release, instead of up to 28 s. A pause that began before 8 s isn't cut at when it gets there: the speculative tail already covers it, and cutting would send that audio twice.
- **Otherwise by 28 s.** Without such a pause, once pending audio reaches 28 s it slides a 0.4 s window over the 18–28 s span and cuts at the centre of the lowest-energy window: the quietest spot always wins. On real speech, cut points land 22–70 dB below speech level.
- Each frame is judged on the frames up to it, so the cuts depend only on the audio, not on how it arrives: a retry hands the saved recording over in one go and reuses the per-chunk transcripts that succeeded by index. A dictation saved by a version that cut differently (`Chunker.layout`, stored with the record) is retried from scratch. `testdata/voice-activity-cases.json` holds cut points both test suites check, fed in blocks and in one go.

### Transcription (`TypelessCore/TranscriptionPipeline.swift`)
- Chunks are transcribed as soon as they're cut, so after release only the tail remains (and often not even that: see [Latency after release](#latency-after-release)).
- Silent chunks are skipped (STT models hallucinate "Thanks for watching!" on silence). Every chunk is sent without the silence before and after its speech, keeping 0.3 s on each side (`VoiceActivity.speechBounds`).
- Per-attempt timeout: `clamp(2 × chunk length + 15 s, 30…90 s)`.
- Retryable: network errors, timeouts, 408/409/425/429/5xx. Permanent: 400/401/402/403, missing keys.
- After the first pass, chunks that failed with a *transient* error get one more full round.
- Transcripts are joined in order, with no space between CJK fragments and a space between Latin ones.
- **Vocabulary hints** (`TypelessCore/VocabularyHints.swift`). The vocabulary (at most 100 terms) goes to the speech-to-text model as spelling hints where the model takes them, not only to clean-up. OpenRouter's normalized `keyterms` field is rejected by every speech-to-text model it serves ("The selected model does not support keyterms", Oct 2026), and `/models` lists no `supported_parameters` for them, so the provider's own field goes through `provider.options` for the models where it was measured to help: Azure `phraseList.phrases` for `microsoft/mai-transcribe-*`, OpenAI `prompt` for `gpt-4o-transcribe`, `gpt-4o-mini-transcribe`, `gpt-transcribe` and `whisper-1`, AssemblyAI `keyterms_prompt`. Direct OpenAI and Groq get a `prompt` form field. A `prompt` is cut at a whole term once it would pass 100 tokens by `TokenEstimate`: Whisper reads only the last 224 tokens and drops the first terms of a longer one, and a Chinese character often takes two (a 600-character cap let 600 Chinese characters through). Measured on two synthetic clips (five invented names in English; four names in Chinese with English, among 40 vocabulary terms): mai-transcribe-2 went from 2/5 to 5/5 and from 3/4 to 4/4, gpt-4o-transcribe from 2/5 to 5/5 and from 1–2/4 to 4/4, whisper-1 from 3/5 to 5/5 and 2/4 to 4/4, and none of the 36 unspoken terms showed up. DeepInfra, Together, Groq-via-OpenRouter, Mistral, Alibaba, Deepgram, xAI, Google and Fish Audio models ignored the fields tried or rejected them (Gemini and Parakeet return 400 for `prompt`), so they get none. A request rejected with 400 while carrying hints is sent again without them.

### Clean-up (`TypelessCore/PolishClient.swift`, `HedgedPolish.swift`, `Prompts.swift`)
- Streaming chat completion with an **idle** timeout (25 s without data) plus a 240 s runaway guard.
- On OpenRouter: reasoning is disabled or set to its minimum based on `/models` metadata, and providers are sorted by latency, with those under 50 tokens/s at the median moved to the back.
- A model's host can be picked on the Models page (the choices come from `/models/{id}/endpoints`). The picked host is sent as `provider.order` and asked first. OpenRouter still falls back to the other hosts, fastest first, if it fails, so the choice never breaks a dictation. Speech to text has no such choice: in Oct 2026, OpenRouter's `/audio/transcriptions` ignored `order`, `only`, `ignore` and `sort` (even `only: ["nosuchprovider"]` succeeded). It picks a host by price, weighted by the inverse square of the price. For `openai/whisper-large-v3-turbo` that sends about 9 in 10 requests to DeepInfra ($0.0000033/s) rather than Groq ($0.0000111/s, billed at least 10 s). To use Groq every time, choose Groq itself as the speech-to-text provider.
- **Hedged requests.** An optional backup model (by default a fast model from another vendor) starts when the main model has produced no token after a fixed 0.55 s, or fails before that. Whichever streams its first token first is kept and the other request is cancelled, so a slow upstream costs about 0.55 s plus the backup's own first-token time instead of the whole wait, and the extra spend is limited to that slow tail. The delay is a constant rather than learned at runtime because flash-class first-token latency is stable: gemini-3.1-flash-lite's first token comes at 0.41 s at the median and 0.49 s at p90, so one still missing at 0.55 s is in the slow tail (see [eval/README.md](../eval/README.md)).
- Each dictation records where the wait went (transcription tail, clean-up first token and total, which model answered) in `session.json`, shown in History, along with what the next analysis needs: whether the speculative tail was used, which speech-to-text route answered the last chunk, how long the clean-up had been running at release, release to delivery, and whether the text was pasted, copied or failed to paste.
- If a server rejects an optional parameter (e.g. `temperature` on reasoning models), the request is retried with the bare minimum.
- Safety nets: echoed wrappers are stripped, and an output far longer than the input (the model *answered* the prompt instead of rewriting it) falls back to the raw transcript, as does one that copied from the text around the cursor (see below).
- The prompt asks for **minimal edits**: only self-corrections, speech noise, recognition errors, punctuation and explicit enumerations are touched; wording, order, tone, pronouns and every word's language are kept. Mixed Chinese/English is preserved word by word (an earlier, more ambitious prompt translated about a third of the English words in real mixed dictations). A one-line reminder after the transcript restates the two rules models drift from most.
- The prompt uses few-shot examples, which proved far more effective than extra rules. It is tuned with `--eval-polish` against a development set, a held-out set and real dictations.

### Translation mode (`TypelessCore/Translation.swift`, `Prompts.swift`, `OpenTypeless/SessionController.swift`)
- Off by default. Once it's on (**Vocabulary & Style → Translation**: a target language, one of nine or any name typed in, and a switch key), holding the dictation hotkey and pressing the switch key (⇧ by default; either side; ⌃ or ⌥ instead) turns that recording into a translation: Fn + ⇧ on macOS, Right Alt + Shift on Windows, as in Typeless. It's a mode chord (see Hotkey below); a modifier-only hotkey's own key is never its chord. The chord's press and release are kept from the focused app, where Shift on its own would switch a Chinese or Japanese input method, or Alt + Shift the keyboard layout. Pressed during the tap that starts hands-free mode, it makes a hands-free translation. The capsule shows the target ("→ EN") while recording and processing.
- **One request.** A dedicated translate prompt (byte-identical on both platforms, checked by a SHA-256 in `testdata/translate-guard-cases.json`) keeps the clean-up's rules (self-corrections resolved, the mess of speaking removed, names, numbers, code and vocabulary kept exactly, never an answer) and writes everything in the target language. It goes through the same `SegmentedPolish` / `HedgedPolish` path (parts for long dictations, the backup model), and the clean-up started ahead of time uses it too: switching modes mid-recording restarts that with the other prompt. OpenWhispr instead sends a translation request after the clean-up, every time; here the second request only happens when the first can't be used.
- **Its own guards.** The clean-up's guards reject every translation by design (it has little in common with the transcript), so a translation is checked for being cut off, much longer than any translation gets, much shorter, and not mostly in the target's script. Lengths are counted so they compare across writing systems (`ScriptShare.length`: a Han character or hiragana is half a word, a katakana loanword one, so technical English into Japanese isn't "longer"); faithful translations come to 0.4–1.33 of their transcript, so over 4× + 40 is an answer and under a quarter of a long transcript (75 such words) a summary. The script check cuts words exactly as `WordCount` does ("e-mail", "foo_bar" once) and leaves out names, code and terms kept as they were: other-script words found in the transcript that read as names (a capital, a digit or a joiner: "TypeScript", "e-mail"), anything in the vocabulary, and Han/kana runs of up to four characters found in the transcript ("Contact 欧阳娜娜."), unless the translation also left a longer phrase untranslated. Of the rest, at least half must be in the target's script, and of everything at least a fifth (all terms and no target-language text wasn't translated either); kana tell Japanese from Chinese. A language typed in isn't script-checked. Ordinary dictation keeps the clean-up's guards, untouched. Cases: `testdata/translate-guard-cases.json`, read by both test suites.
- **Falling back.** A translation with any unusable part is set aside as a whole (half-translated text helps nobody); the clean-up of the transcript goes in instead (one more request, when clean-up is on), and the transcript as spoken when that fails too, with a notice in the capsule and the reason in History. The set-aside translation is billed and counted, also when Esc stops the clean-up that replaces it (its answer is kept as it comes in, `PolishLedger`).
- History saves `mode: "translate"` and `targetLanguage` (absent for plain dictation, so older records and older versions are unaffected), shows "Translation → English" in the details, and Re-transcribe or Retry translates again into the same language. Edits to an inserted translation aren't learned from: they say nothing about what speech recognition misheard. Speech recognition's language stays as configured.
- Not done: a shortcut of its own that starts a translation directly (an action shortcut fires only between dictations by design, and a hands-free toggle would need it to act during one).

### Command mode: editing selected text by voice (`TypelessCore/SelectionCommand.swift`, `Prompts.swift`, `OpenTypeless/SelectedText.swift`, `SessionController.swift`)
- Off by default (**Shortcut → Edit selected text by voice**: a switch and a switch key, ⌃ by default, or ⇧ / ⌥). Select text in any app, hold the dictation hotkey and press the switch key: that recording is an instruction for the selection ("make it more formal", "translate to English", "fix the grammar", "把这段改成要点列表"), and the selection is replaced with the result: Fn + ⌃ on macOS, Right Alt + Ctrl on Windows. Like Wispr Flow's Command Mode and VoiceInk's edit, but only ever on its chord: Aqua's edit mode switches on whenever text is selected as the dictation starts, which turns a selection left over by accident into an instruction. Without the chord nothing is read, and a dictation is what it always was. It's a mode chord (see Hotkey below), registered next to translation's; when both are on with the same key, translation keeps it and Settings says so. The capsule shows "✎ Edit". Pressed during the tap that starts hands-free mode, it makes a hands-free edit.
- **Reading the selection** happens as the chord goes down, while the app with the selection is in front (`SelectionReader`, the order of SelectedTextKit, behind VoiceInk): Accessibility's `kAXSelectedTextAttribute` / UI Automation's `TextPattern.GetSelection`, which press nothing; on macOS the app's own Edit ▸ Copy, found by its ⌘C shortcut and pressed through Accessibility (no keys, so the hotkey and chord still held don't matter; a disabled one means nothing is selected); last ⌘C / Ctrl+C, sent only once every key is let go of (after a push-to-talk recording, then) and only into the same window, the clipboard put back as it was. Refused before anything is read: terminals (a paste there runs as commands, and Ctrl+C interrupts) and password fields (`AXSecureTextField`, UIA `IsPassword`; neither copy runs while macOS secure input is on). In code editors whose copy takes the whole line when nothing is selected (VS Code, Cursor, JetBrains, Sublime, Zed, Nova, Pulsar; Visual Studio and Notepad++ on Windows) only an Accessibility / UI Automation selection counts. Accessibility calls run off the main thread, where the hotkey's event tap lives, each batch with a 0.6 s deadline and every element (menu items included) with a 0.25 s timeout, so an app slow to answer can't hold the user's keys up. A copy that lands only after the 400 ms wait still has the clipboard put back. Over 6,000 characters is refused (Aqua's cap: a longer rewrite takes long to stream, and a cut-off one can't go over the text). A selection that can't be edited stops the recording at once with the reason in the capsule; one only found missing after the keys are up (by copying) is reported then. Nothing is ever pasted or copied in either case.
- **One request, the selection as data.** The command prompt (byte-identical on both platforms, SHA-256 in `testdata/command-cases.json`) says the selection is data and only the spoken instruction is an instruction; the user message puts the selection in `<selection>`, then the instruction in `<instruction>`, then a reminder. Neither can close its block: a `<` that would open one of those tags (any case, with a slash, spaces, line breaks or zero-width characters in between) becomes a look-alike ‹, and nothing else is touched, so code and markup come back exactly; the output's look-alikes are turned back (unless the selection had look-alike tags of its own). The vocabulary, mishearings and preferences follow as in the clean-up. One request, never split in parts, hedged with the backup model and retried once like a clean-up, with `max_tokens` at three a character of selection and instruction (up to 16,384) and a timeout sized by the selection. A question about the text comes back after `[[ANSWER]]` (OpenWhispr marks questions the same way): it's shown in the capsule and copied, never pasted over the selection.
- **Its own guards.** The clean-up's guards don't apply (a rewrite has little in common with the instruction, and "shorten it" or "translate it" change its length a lot). Taken out first, each only when the selection didn't have one itself, in any language (a translation translates it): the selection's tags; a code fence or quotes around the whole answer, unless the instruction asked for them ("put it in a code block", "加上引号"); a preamble line that talks about the edit ("Here is the more formal version:", "以下是修改后的文本：", not "Okay, so the plan is:"), unless the selection's own first line ends in a colon; and a labelled closing note ("Note: I fixed…", "（注：…）", not "I've attached the report."). Then the answer is refused when cut off (finish reason), empty, or a refusal / question back about the request ("I'm sorry, but I can't help with that", "Could you clarify…", "抱歉，我无法完成…"), unless the selection apologises itself ("抱歉，我来不了" becomes "Sorry, I can't come"). A selection that starts with `[[ANSWER]]` is never read as a question. A rewrite identical to the selection pastes nothing ("Nothing to change"). Cases: `testdata/command-cases.json`, read by both test suites.
- **Delivery.** The rewrite keeps the white space the selection started and ended with, and its line endings, and is pasted over the selection (so the app's Undo takes it back) only while the same app, window (by its title too: a browser's tab) and focused element are in front, focus can take text, the screen is unlocked and Esc hasn't come, and the selection can't have moved: read by Accessibility / UI Automation, it's read again and must be the same; read by copying (or not readable again), no click or key may have reached an app since (macOS counts the keys its tap lets through and the session's mouse-down counters; Windows counts in its hooks). The app, the clicks and keys and the lock are checked again right before ⌘V. Otherwise it goes to the clipboard, with the reason in the capsule. Return is never pressed after an edit, and edits aren't learned from.
- History saves `mode: "command"`, the instruction as the transcript and the selection's length (`selectionLength`), never the selection or the rewrite (or the answer about it): they can be anything the user had open, and History keeps entries for days. Without it an edit can't be run again, so Re-transcribe, the menu bar's Retry and Paste last dictation pass over edits.

### Spoken line breaks (`TypelessCore/SpokenLayout.swift`)
- "New line" and "new paragraph" become a line break and a blank line, opt-in (Settings → General, off by default: see the false positives below). The commands, compared lowercased and without spaces (so "New Line", "newline", 줄 바꿈 and 줄바꿈 are each one): line — new line / newline, 换行 / 換行, 改行, 줄 바꿈 / 새 줄 / 새로운 줄, nueva línea, nova linha, à la ligne / nouvelle ligne, neue Zeile, новая строка; paragraph — new paragraph, 新段落 / 另起一段 / 换一段 / 換一段, 新しい段落 / 改段落, 새 단락 / 새 문단 / 새로운 단락 / 새로운 문단, nuevo párrafo, novo parágrafo, nouveau paragraphe, neuer Absatz, новый абзац (accent-less spellings too). Every language's commands are recognised in any dictation.
- It runs on the transcript before the clean-up, by rule rather than by the model: a command counts only when it is a whole clause, between punctuation (speech recognition writes the pauses around a command said on its own as punctuation) or at the start or end. "Add a new line to the config", "这里要不要换行", a command run into the words around it without a pause, behind a dash, or in quotes stays as words. The punctuation before a command stays, the command and the punctuation after it go.
- Known false positives, pinned in the fixture: a command word said as its own clause in a list ("spaces, new line, tabs", "空格，换行，制表符"), as reported speech without quotation marks, as the topic of a question ("换行，是怎么实现的") or as a one-word answer becomes a break. That is one visible line break, undone with one key, and why the feature is off until the user turns it on (the toggle's subtitle mentions the list case).
- Ordinary dictations are untouched: a transcript without a command is left byte for byte as it came, and its clean-up gets the prompt it always had, speech recognition's own line breaks (some services break at their segments, mid-sentence) included. When a command was said, those breaks become a space (none between Chinese or Japanese characters) first, so every break left is one the speaker asked for; only then does the clean-up get a "## Line breaks" section asking to keep them (`dictatedLineBreaks`, added only for a transcript or part that has one), with an example. A long transcript split at a dictated break gets exactly that break back between the parts' clean-ups.
- `SpokenLayout.layout` gives what the dictation uses: the laid-out text is the record's raw text (what goes in when clean-up is off or fails, and what a cancelled recording kept in History holds); breaks at the very start or end are kept out of the clean-up, whose answer is trimmed, and put back around its text; a clean-up started ahead of time is given the same text and compared by the whole layout. `testdata/spoken-layout-cases.json` holds the cases (every language, the limitations, line endings, decomposed accents and Hangul, ideographic and no-break spaces), read by both test suites.

### Latency after release (`TypelessCore/VoiceActivity.swift`, `Preconnector.swift`, `TranscriptionPipeline.swift`, `OpenTypeless/SessionController.swift`)
What the speaker waits for is the time from letting go of the key to the text at the cursor. Most dictations are shorter than one chunk, so without the steps below the whole recording would only be sent at release.
- **Warm connections.** When the key goes down, a HEAD request (no key) goes to each distinct host the dictation will use: speech-to-text and clean-up, main and backup routes. Any answer leaves a warm connection in the shared session / `HttpClient` pool, so the first real request doesn't pay for DNS, TCP and TLS. Repeated every 25 s while recording, so the clean-up's connection, idle while speech-to-text works, doesn't time out; a host is warmed at most once every 20 s.
- **Speech and pauses** (`VoiceActivity`, `PauseTracker`). 30 ms frames; a frame is speech above twice the level of the quietest tenth of the frames, clamped to 0.004–0.008 RMS (about −48 to −42 dBFS). The floor is the level silent chunks are skipped under; the ceiling keeps a softly spoken word from being taken for a pause, while a noisy room still has pauses. `testdata/voice-activity-cases.json` holds cases both test suites read.
- **Speculative tail.** People stop talking a moment before they let go of the key. Once the speaker has been quiet for 0.3 s after speaking, the audio not yet cut into a chunk is sent for transcription. If they speak again, that request is cancelled (or its answer dropped) and the next pause starts another; if they let go without saying anything more (only silence since, apart from the last 150 ms: the key's click as it's let go, or a breath, which used to void it), its answer is the last chunk's, and the text is there as soon as that request is. Chunk boundaries don't change, so neither does the transcript. A chunk cut while it is out cancels it too; with 8 s or more pending, the pause is cut at instead (see the chunker), and a last chunk that is then only the rest of that pause and the click isn't sent. Answered requests count toward the cost, dropped ones included.
- **Clean-up ahead of time.** When a speculative tail and every chunk before it are transcribed, the pipeline passes the whole transcript to the app, which starts the (hedged) clean-up on it, with the text around the cursor read so far. At release, if the final transcript is that exact text and the text around the cursor is the same, the running or finished clean-up is used; otherwise it's cancelled. History's clean-up times count from the release. A clean-up that finished and was then dropped because the speaker went on was billed and is counted.
- **Bookkeeping after the paste.** Costs, the usage ledger and History (with its retention pass) are written after the text is inserted; the transcript is saved while the clean-up runs.

### Delivery (`OpenTypeless/FocusProbe.swift`, `TextInserter.swift`)
The Accessibility API is asked what has focus:
- **Editable** (text field, text view, editable web content): paste with ⌘V, then restore the previous clipboard.
- **Clearly not editable** (desktop, lists, buttons in native apps): copy to the clipboard.
- **Unknown** (browsers and Electron apps that don't expose their page tree, e.g. Firefox): paste *and* leave the text on the clipboard.

Right before a paste, the text is fitted to the field (`TypelessCore/InsertionJoiner.swift`, on by default): the characters either side of the cursor are read (`AXSelectedTextRange` + `AXStringForRange`, 0.3 s for the whole read), and the paste gets a space where it would run into the word before or after it (or between Chinese and Latin text, as the clean-up prompt writes it), a lowercase first word in mid-sentence when the spelling dictionary knows it as an everyday word and it isn't "I", an acronym, a word with inner capitals or a vocabulary term, and no final "." / "。" when the text after the cursor carries the sentence on. Characters are judged by the base of each grapheme (an accent written as a combining mark doesn't hide the "e"), and Han counts in every plane. OpenWhispr always adds a trailing space unless the text is CJK, and whisper-writer and Handy add one or drop the final period by setting; here the actual neighbours decide, and any doubt leaves the text as it is: either side unreadable, a field not known to be other than a password field, secure input, a terminal, a cursor reported at the very start (some apps say that when they don't know), a cursor inside a word, a read that doesn't add up or runs out of time, or a multi-line text. The fitted text is bound to the field and selection it was read at: right before ⌘V (after the clipboard is prepared) both are checked again, and if either changed or can't be checked in time, the promised pasteboard data becomes the cleaned text instead. Only the paste is fitted: History keeps the cleaned text, whatever is left on the clipboard (the fallback, a paste that didn't land, Restore clipboard off) is the cleaned text, the edit watcher compares against what was actually pasted, and the session log says what was adjusted.

**Finish and send** (`TypelessCore/SendKey.swift`): an optional send key (Return, ⇧Return or ⌘Return; off by default, stored by name under `sendKey`, unknown names read as off) that, pressed while recording, ends the recording like letting go of the hotkey (or, hands-free, tapping it) and is pressed again in the app once the text is pasted there, in place of "Press Return after inserting" for that dictation. The tap only watches for it while the session is recording (set synchronously as the state changes), matches Return or the keypad's Enter with exactly the key's modifiers, those of the held hotkey aside, and swallows its key-down, repeats and key-up, so no Return reaches the app before the text. One within 0.4 s of a held hotkey going down is a key combination (Fn+Return) and is left as it was. The send is only pressed when the paste landed in the app that was in front when the recording stopped and that app is still in front, the dictation is still current (not Esc'd, not followed by another) and the screen hasn't locked: whatever puts the text on the clipboard instead sends nothing. It waits for the send key's keys and every modifier to be let go first (2 s at most, then the text is left unsent), since Return read with a modifier still held is another key. Settings warns when the dictation hotkey is a combination on Return, which would take the send key's presses first. The Windows hook ignores an Enter injected by other software (it goes through); macOS has no equally reliable mark for synthetic keys, so there only the app's own (`eventSourceUserData`) are told apart. As with "Press Return after inserting", the target is checked by app (macOS) or window (Windows), not by text field. There is no spoken "send it": a send can't be taken back.

### Learning from corrections (`OpenTypeless/EditWatcher.swift`, `TypelessCore/CorrectionLearner.swift`)
Like Wispr Flow and Typeless, fixes the user makes to pasted text grow the vocabulary.
- After a paste into a field whose Accessibility value contains the dictated text, that field is read twice a second, locally. Secure fields and very large fields are skipped.
- Many apps don't expose their fields that way: the learning log of one week of real use had all 205 watches fail before starting (WeChat, Claude, Discord and Codex: no focused field; Firefox: value unreadable). On macOS the focused element is now asked of the app itself first (as typeless-local and OpenWhispr do), a focused window counts as none (a dormant Chromium tree reports the window), and an app that shows none is switched on with `AXManualAccessibility`, then asked again up to five times 0.3 s apart while Electron builds its tree. `AXEnhancedUserInterface` is never set: it puts the app in screen-reader mode, which in Chromium apps such as Claude takes keyboard focus away from the field (OpenWhispr found every later dictation then pasted nowhere). A field with no plain value (rich editors, web content) is read with `AXStringForRange` over its whole length. Where the field still can't be read (WeChat, ChatGPT's composer, which shows no element whatever is switched on), the keys pressed after the paste are followed instead (`TypelessCore/TypedEdit.swift`): the dictated text with the cursor at its end, then typing, Backspace / Delete, the arrows and word jumps, with or without a selection. A click loses the cursor; a word then selected by double-clicking or dragging finds it again: the selection is read from Accessibility, or else copied with ⌘C / Ctrl+C and the clipboard put back, and located in the dictated text when it occurs there exactly once (so a double-click on the misheard word, then typing over it, is followed like it is in Typeless). Whatever it can't follow exactly ends the watch, and the state before it is judged: a key typed while the cursor is lost (after a plain click), a context menu, another app, Return / Tab, shortcuts such as undo, the cursor leaving the dictated text (what's around it is unknown), word jumps across CJK text (dictionary word boundaries), and text typed through an input method such as Pinyin, whose keys spell a word before it's chosen. On Windows the keyboard hook reports each key with the text it types in the foreground app's layout (`ToUnicodeEx`), and a mouse hook runs only while keys are followed; Ctrl+→ and Ctrl+Delete aren't followed there, since they stop at the start of the next word.
- The watch ends when focus leaves the field, the field is sent or cleared (the dictated text can no longer be located), a new dictation starts, or after two minutes. Only that final state is compared, so half-finished edits (a known failure mode of eager learners) are never learned.
- The dictated span is diffed against its edited version token by token (Latin words, single CJK characters). A fix inside Chinese text is then widened to the word it belongs to, using the system word segmenter on the edited text (`NLTokenizer` on macOS, `Windows.Data.Text.WordsSegmenter` on Windows), so correcting one wrong character of 罗级鼠标 learns 罗技, heard as 罗级. Names the segmenter doesn't know come out as single characters (千|问, 飞|书), so a fix that is still one character takes in the neighbouring one-character words, up to 4 characters; a fixed particle (的/地/得…) is never widened.
- A replacement is learned only if it sounds alike, keeps the same digits, isn't a first-letter capitalisation, isn't one ordinary English word swapped for another (system spell checker), and the whole edit isn't a rewrite (similarity ≥ 0.5, ≤ 5 changes). "Sounds alike" is either spelling (edit distance ≤ 0.5 on a pinyin/Latin key, so 逻辑 → 罗技 and "TypeList" → "Typeless" qualify but "Mike" → "Sarah" doesn't) or sound: each word, Chinese as pinyin, reduced to its consonant sounds with a simplified Metaphone, within a third of each other. The sound key catches English spelt differently ("Versel" → "Vercel", "Cooper Netties" → "Kubernetes") and English terms heard as Chinese (克劳德 → Claude, 杰森 → JSON, 瑞艾克特 → React).
- Every paste is recorded in `learning-log.jsonl` in the data folder: the app, whether its field could be read (and if not, why: no focused field, text unreadable, dictated text not found, with whether it would match ignoring spaces), why the watch ended, and each replacement with the reason it wasn't learned. Local only, trimmed to the newest half past 512 KB.
- New terms are appended to the vocabulary; the misheard forms go into the clean-up prompt as hints. Removing a learned term blocks it from being learned again.

### Snippets (`TypelessCore/Snippets.swift`)
Like Wispr Flow's snippets: a spoken trigger (up to 60 characters, "my email", "我的邮箱", "PR template") is replaced by its expansion (up to 4,000 characters, line breaks allowed), word for word, anywhere in the dictation. None exist by default.
- **In code, after clean-up.** The expansion is done on the final text right before delivery (the cleaned-up text, or the transcript when clean-up is off or fell back), never by the model: asked to keep a long template as is, a model paraphrases or translates it, and the clean-up's guards would take the longer output for an answer. Like Superwhisper's replacements, and unlike asking the LLM. It's a pure function of the text and the snippets, so a retry inserts what the first run would have with the same snippets.
- **Triggers come through as written.** They go ahead of the vocabulary in the speech-to-text hints and the clean-up prompt (hints stop after the first terms), so recognition spells them right and the clean-up keeps them.
- **Matching.** Text and trigger are compared a whole character (grapheme cluster) at a time, each in its canonical composition (NFC) and folded: lowercase, full-width ASCII as ASCII, every run of spaces or line breaks as one space and none next to Chinese or Japanese (the clean-up writes "我的 GitHub" for 我的GitHub). So "é" matches e + ◌́ and a Hangul syllable its jamo, a trigger never takes part of a character ("か" isn't found in "が" typed as か + ◌゙), and the same key tells duplicate triggers apart on both platforms. Scripts are told apart by one classifier that covers every block (supplementary-plane Han such as 𠮷, Hangul jamo). Word boundaries count only at a trigger's Latin edges: OpenWhispr's `\b` regex can't find 我的邮箱 in 发到我的邮箱吧, while "email" must not match inside "emails". Next to Hangul nothing is required either, since Korean particles attach to the word before. Overlapping triggers go longest first ("my address in English" over "my address"), and the text is searched once, so an expansion is never searched for other triggers (OpenWhispr replaces trigger after trigger on the result).
- **Joining.** A dictation that is only the trigger and its punctuation becomes exactly the expansion (no "." after an address or a template). After an expansion that ends in punctuation or has several lines, the clean-up's punctuation after the trigger, and any spaces before it (French "réponse !"), is dropped ("…回复你。。" would double it), never across a line break. Where an expansion meets a Latin word, or Chinese/Japanese meets Latin, a space goes in, the way the clean-up spaces mixed text ("发到 tyler@example.com 吧").
- An expansion is saved exactly as typed (indentation, final line break); only the trigger is trimmed. The saved list is read entry by entry, so one damaged entry doesn't hide the others, and an entry without an ID of its own is given one and saved, so editing and deleting it work.
- History keeps the spoken text (cleaned up or raw) and, when snippets changed it, the inserted text; word counts and the Home page go by what was said. Both test suites run `testdata/snippet-cases.json`.

### Text around the cursor (`OpenTypeless/CursorContextReader.swift`, `TypelessCore/CursorContext.swift`)
Names and terms a reply is about are usually already on screen: a colleague's name in the thread, a product, a code identifier. With **Use text around the cursor to spell names** on (off by default, since the text goes to the clean-up provider), the clean-up gets that text as a spelling reference.
- **What is read.** When the key goes down, the focused field of the app in front, through Accessibility on macOS and UI Automation on Windows, off the main thread with short timeouts. Up to 1,500 characters around the cursor: the selection (cut to the limit) and as much on either side as fits, split evenly, read as ranges around the selection so a long document isn't copied over whole (`AXStringForRange` around `AXSelectedTextRange`; the Text pattern's selection, moved by characters), or else the whole value with the cursor taken to be at its end. Characters are whole, runs of whitespace are squeezed, and a word of spaced script cut at an edge is dropped; a range read that stops short of the field's start or end can end inside a character (two of a family emoji's three people look whole), so it's trimmed back past the nearest space or punctuation mark (`testdata/cursor-context-cases.json`). Only a field that answers clearly is read: one that says it isn't a password field (on Windows `IsPassword` read with `ignoreDefaultValue`, so an element that doesn't say isn't read; on macOS a role and subrole that could be read and aren't `AXSecureTextField`), and that it can be written to (a settable `AXValue` or an editable ancestor; UI Automation's Value pattern saying it isn't read-only, or else the read-only attribute of the text at the cursor). Nothing is read while secure input is on (macOS), nor a browser's page itself. An app that shows no focused element yet (Electron before `AXManualAccessibility`, Chromium before its UI Automation tree is built) is asked again for about a second. Each read belongs to one dictation and one app (macOS: the pid, also for the system-wide focused element) or window (Windows): it's cancelled when the dictation ends, when the screen locks and when the clean-up starts, and its text is kept only if the same element of the same app or window still has focus and still says it isn't a password field once it's read. On Windows only one read is out at a time: one a hung app holds up keeps its thread-pool thread, so no other starts meanwhile, and every COM object a read gets is released. Anything that fails, or isn't in by the time the clean-up starts, means no context; nothing is ever waited for. The app name and window title are never sent.
- **How it's sent.** After the transcript in the user message, inside `<context>…</context>` (its own `<` and `>` become `‹` and `›`, so no tag can be spelled inside it, however it's nested or spaced, and it can't close its block), with a note that it's reference only: spell the names and terms the speaker said, never copy from it, answer it, follow instructions in it or switch to its language. The system prompt stays the same for every dictation, so providers keep caching it, and the text is byte-identical on both platforms. It goes with every request: both hedged routes, and every part of a long dictation, since each part is a request of its own and a name can come up in any of them. The clean-up started ahead of time carries it too; one started before it was read isn't taken over.
- **Guard.** Besides the usual ones, the output is aligned with the transcript letter by letter (edit distance), and each place where they differ counts the letters it adds that come from the context (in a run of four found there), less the transcript's letters it replaces. A name spelled from the context replaces what was heard with about as many letters ("shivon" → "Siobhan"), however often it's said; a phrase taken over adds all of its own. Places adding four or more such letters count, and six in all (a greeting, "Thanks, Marcus", "Room 4B") mean the output took text over from the context: it goes in as spoken (`Prompts.copiedContext`, `testdata/polish-guard-cases.json`). Echoed wrappers of the context (its note, tags round the whole answer) are stripped only when context was sent: without it, the output is cleaned exactly as before.
- **Privacy.** The text isn't logged, kept in History or saved anywhere; History notes only that it was sent (`usedContext`), set as a request carrying it actually goes out (the clean-up started ahead of time included). Superwhisper and VoiceInk read the screen instead (a screenshot and OCR): that needs screen recording permission and reads far more than the field. Accessibility text is exact, cheaper, and limited to where the speaker is typing.

### Backup speech-to-text (`TypelessCore/TranscriptionPipeline.swift`, `TranscriptionLatency.swift`)
Optional, off by default. Each chunk goes to the main route first. When it is late, or the main route fails, the backup route is asked too; the first answer wins and the other request is cancelled (like the clean-up hedge).
- **When a chunk is late.** Fitted on 128 timed dictations (`microsoft/mai-transcribe-2` through OpenRouter, 1–27 s chunks): the wait barely grows with length, about 0.39 s + 0.02 s per second of audio (Theil–Sen line through the chunks left after dropping those more than three MADs above it; residual MAD 0.35 s). Most answers land on the line; a slower mode around 1.6–2.3 s and the odd 4.7–10.6 s answer don't. Only the last chunk is usually waited on and speech-to-text is cheap next to the wait, so a chunk is late 0.2 s past the line (0.63 s for a 2 s chunk, 1.15 s for 28 s), clamped to 0.5–25 s; in that data about 40% of last chunks would ask the backup. A route that is slower or faster across the board moves the line by the median of its last 20 residuals once three chunks are timed; the median ignores the odd very late answer. (The previous rule, twice the median wait ÷ audio-seconds ratio plus a second, carried a short chunk's fixed overhead over to long chunks: replayed over the same dictations, chunks of 15 s or more waited 3.9–13.7 s before the backup was asked, against 0.9–1.2 s now.)
- **Only once the recording has ended.** A chunk sent while the user is still talking holds nothing up, so it isn't hedged for being late (only for failing); when the recording ends, a chunk still out that is already past its deadline is asked of the backup at once, and the others at their deadline. The backup is paid for mainly on the last chunk, the one the text waits for.
- **The last chunk is raced.** A chunk sent after the recording has ended, with at most 10 s of audio, goes to both routes at once instead of waiting for its deadline: in 789 timed sessions the backup won 13% of the time, and then the text still took 1.79 s at the median, mostly the wait before asking it. Longer chunks keep the deadline, so two uploads of them don't share a slow uplink.
- Backup answers are priced with the backup's model, and History's timing line counts them.

### Microphone (`OpenTypeless/AudioRecorder.swift`, `Microphones.swift`, `TypelessCore/AudioSink.swift`)
- **Choosing the input.** CoreAudio lists the inputs (a device's UID is remembered, since device IDs change); the chosen one is set on the engine's input unit (`kAudioOutputUnitProperty_CurrentDevice`) before the engine starts, and a device that isn't connected falls back to the system default. Virtual and aggregate devices are labelled. General → Microphone has a Test button with a live level meter that listens only while testing.
- **Keeping it ready.** Samples always pass through `AudioSink`. With **Keep microphone ready** on, the recorder keeps running between dictations and the sink holds the last 0.4 s; when a dictation starts, that pre-roll is handed over first and the rest follows in order, under one lock. So recording starts with no device start-up delay (Bluetooth headsets take a noticeable moment) and includes the start of a word spoken as the key goes down. The pre-roll doesn't count toward the accidental-tap and Esc thresholds. Off by default, since the microphone indicator stays on and Bluetooth headphones switch to call mode.

### Esc (`TypelessCore/CancelPolicy.swift`)
A recording under 10 s is discarded as before. From 10 s on, Esc stops recording and inserts nothing, but the rest of the recording is transcribed in the background (no clean-up), and the dictation is kept in History with status `cancelled`, where it can be copied or re-transcribed. Esc while processing keeps what was transcribed the same way. Cancelled dictations are removed 24 hours after they were made, whatever the retention setting.

### Live preview (`OpenTypeless/LivePreview.swift`)
Optional (beta). While recording, the words recognised so far appear above the capsule. macOS runs `SpeechAnalyzer` with a `SpeechTranscriber` reporting volatile results, fed the same 16 kHz samples being recorded (converted to the analyzer's format); a language used for the first time has its model downloaded in the background and previews from the next dictation. It is never used for the result: the inserted text still comes from the speech-to-text provider. `LivePreviewText` keeps the last 60 characters on one line without splitting a character.

### App profiles (`TypelessCore/AppProfiles.swift`, `OpenTypeless/SessionController.swift`, `AppsPage.swift`)
Optional: there are none until the user adds one under Settings → Apps. A profile names an app (a bundle ID on macOS; an executable name on Windows, compared case-insensitively and with or without `.exe`) and can override four settings: clean-up on or off, Return (Enter) after the paste, the spoken-language hint (a language or auto-detect), and extra clean-up preferences. Whatever it leaves on Default follows the global setting. Like VoiceInk's modes and Superwhisper's per-app switching.
- **Picked once.** When recording starts, the frontmost app (on Windows the foreground window's process, or for a Store app the process behind `ApplicationFrameHost`'s frame) picks the profile, and the resulting `DictationSettings` drive everything that dictation does: the language of every chunk on both speech-to-text routes, the live preview, which connections are warmed, the clean-up started ahead of time, the segmented and hedged clean-up with its backup model, the HUD's bar, and the Return after the paste. Switching apps before letting go doesn't change them, since the text was spoken for the first app.
- **Never into an app with other settings.** If the app in front when the key is released, or when the text goes in, would get other settings than the app the recording was started in (another profile, or one where the first had none, or none where it had one), the text goes to the clipboard and Return isn't pressed: a chat app's "send" profile never presses Return in a terminal the speaker switched to. Without profiles on either side, delivery is as before (the usual check sends the text to the clipboard when focus moved after the release).
- **Preferences are added, never substituted.** The profile's instructions follow the global preferences in the prompt's "Additional preferences from the speaker" section, after the tuned instructions. Nothing about the app goes to the model, neither its name nor a window title (as in tover0314-w/opentypeless's app detector): only what the user wrote.
- **Matched by app only.** VoiceInk also matches browser URLs, read through AppleScript; that needs Automation permission for each browser and can stall the start of a recording, so it's left out.
- **Retry.** `session.json` keeps the profile's ID and name (`profileID`, `profileName`; absent when none applied). A retry from History uses that profile while it still exists, otherwise the global settings. History shows the name with the dictation's details. The language hint the chunk transcripts were made with is kept too (`chunkLanguage`, "" for auto-detect), and a retry reuses them only when its own hint is the same; a record from before it was kept counts as auto-detect, so a retry with a fixed language sends all its chunks again rather than reuse ones that may be in the wrong language.
- Stored as a JSON array under `appProfiles` (UserDefaults on macOS, `settings.json` on Windows). Unset overrides aren't written, fields one version doesn't know are ignored by the other, and an entry that isn't a profile is skipped without losing the rest. A missing or repeated ID is replaced once when the profiles are loaded, and saved, so it stays the same. `testdata/app-profile-cases.json` holds matching and resolution cases both test suites read.

### Transcribing files (`TypelessCore/FileTranscription.swift`, `AudioFileDecoder.swift`, `OpenTypeless/FileTranscriber.swift`)
History's **Transcribe File…** button, a drop on History, or Finder's Open With offers audio and video files in a sheet with each file's length, the speech-to-text estimate when the model has a per-minute price (a ceiling: silence isn't sent) and a **Clean up text** switch. Each file becomes a History record marked `source: "file"` with its `sourceName`, and goes through the same pipeline as a dictation, one file at a time:
- **Decode into the recording.** The audio track is read as 16 kHz mono (`AVAssetReader` on macOS; Media Foundation's `MediaTranscoder` to a PCM WAV on Windows) into `audio.partial.wav`, renamed to `audio.wav` once all of it is there, so Re-transcribe works as for a dictation and a recording only ever exists whole. A missing file, one that may not be read, a damaged or unsupported one (DRM included), one with no audio track, and a full disk each get their own message on the record.
- **Feed it from disk.** The recording is handed to the pipeline 10 s at a time (`WAVFileReader`, `FileTranscription.feed`), held back while 4 chunks are still out, and the pipeline lets go of each chunk's audio once it's answered (a failed one keeps it for `finish`'s last round), so an hour of audio (about 115 MB) is never all in memory. The transcripts so far are saved every 20 s, and on quit, so a retry only sends what's missing. Before reading, a recording that won't fit on the disk (32 KB a second, and 64 MB to spare) is refused.
- **Stops when it can't succeed.** After a chunk the provider turns down as it would any request (no key or a bad one, no credit, no such model: 401/402/403/404) or 3 failed chunks in a row (each after its retries), the file stops handing out audio and fails with the text so far, retryable, instead of reading the rest only to send requests that fail too. A dictation's pipeline never stops early.
- **Never in the way of dictating.** A file sends at most 2 speech-to-text requests at once (a dictation has its own 3) on a URLSession/HttpClient of its own (3 connections per host), so a dictation's requests never wait for a connection behind a file's; it hands out no new audio while a dictation is under way, has no speculative tail, keeps its own latency estimate, and cleans up 2 parts at a time, each part waiting to start while a dictation is under way. Nothing is pasted.
- **Accounting.** What a file costs is counted; its words and length aren't added to the Home page's dictation totals (an hour-long meeting would swamp them), and the popover's Retry never offers a file.
- Cancel while reading or queued drops the new record; while transcribing it keeps the recording and the transcripts so far, retryable. A file still being read at quit shows as interrupted, to be transcribed again. On Windows, a cancelled transcode's output is deleted once the transcoder lets go of it, and a session folder left with neither `session.json` nor a recording is swept at launch (macOS can delete open files, so it never leaves one).
- A file's recording counts toward History's 1 GB of recordings like any other, so a very long file can take the recordings of the oldest finished dictations (never the newest 10); its text always stays.

### Hotkey (`OpenTypeless/Hotkey.swift`)
- A session-level `CGEventTap` (default tap, which only needs Accessibility).
- A modifier-only hotkey is tracked through `flagsChanged`. Combinations are matched on `keyDown` and swallowed.
- A short tap (< 0.35 s) switches to hands-free mode.
- Another key pressed *with the hotkey's modifier flag* within the first second is treated as a key combo (Fn+F1 …) and cancels the dictation. Keys injected by other apps at the same moment, such as Logi Options+ when a mouse button is remapped to Fn, don't carry the flag and are ignored.
- **Mode chords** (`TypelessCore/HotkeyPress.swift`, `ModeChords`): a second key *registered* as a chord switches the running recording's mode instead of cancelling it, for as long as the hotkey is held, and is kept from the focused app. Translation mode registers its switch key's two sides while it's on, and command mode its own (left to translation when the two are the same); with none registered, every other key is read as above. A modifier chord is followed through `flagsChanged` (its own side's flag tells press from release) and only counts while the hotkey is held. On macOS every event carries the modifiers held, so until a swallowed modifier's release the flags of everything let through (keys, the hotkey's own release, and mouse events, through a second tap that's only on meanwhile) are cleared of it (`SuppressedModifiers`): otherwise the focused app would see Shift held and never let go. A key pressed meanwhile isn't let through at all (`HotkeyPress.keepsFromApp`; it still makes a combination that cancels the dictation): without the modifier it would be another shortcut (⌘⇧Q, log out, as ⌘Q, quit). Windows does the same, since a swallowed modifier never reaches the key state there. The rest of a swallowed press (auto-repeats, release) is swallowed before anything else is looked at, so recording a shortcut or changing Settings meanwhile doesn't let half a key press through; after a tap outage, swallowed keys no longer held are forgotten.
- **Action shortcuts** (`TypelessCore/Shortcuts.swift`): besides the dictation hotkey, each `ShortcutAction` can have a shortcut of its own, unset by default and stored under `shortcuts` by action name. It fires on key-down (`ShortcutMap`: the same key with exactly its ⌃⌥⇧⌘), its keys are always swallowed, and the session ignores it unless idle. Settings refuses a modifier on its own, Esc, the dictation hotkey or another action's keys (`ShortcutConflict`), and the dictation recorder refuses an action's keys. The first action is **Paste last dictation**: `LastDictation` picks the newest dictation that finished with text and pastes it again through `TextInserter` (clipboard restored); when the newest one failed with its recording saved, it's retried and pasted instead, like the menu bar's Retry. The paste waits until the shortcut's keys are physically let go (`HotkeyMonitor.waitForRelease`, 3 s at most, then the clipboard): a posted ⌘V carries its own flags, but some apps go by the modifiers held, and on Windows `SendInput` combines with them. It goes only to the app that was in front when the shortcut was pressed (from the menu-bar panel's button: the app in front before the panel), checked again right before ⌘V; a retried one carries that app as its paste target, like a dictation, Return included. A new dictation, Esc or the screen locking drops a pending one, and it writes nothing to the clipboard or the HUD after that. Keys the app posts itself (⌘V, ⌘C, Return) carry a mark in `eventSourceUserData` and pass the tap untouched, so an action set to ⌘V can't swallow a dictation's paste (the Windows app marks its `SendInput` keys the same way). The saved shortcuts are read and changed one entry at a time (`StoredEntries`), so one this version can't read is kept.

## Persistence

`~/Library/Application Support/OpenTypeless/Sessions/<timestamp>/`:
- `audio.wav`, written while recording.
- `session.json`: status, raw text, cleaned text, the text inserted when snippets changed it, and per-chunk transcripts, so a retry only re-sends failed chunks; for a transcribed file, `source: "file"` and the file's name.

A session found in `recording`/`processing` state at launch is marked failed-but-retryable.

Retention is a user setting: don't keep recordings, 1 day, 7 days, 1 month (default), 1 year, or forever. Recordings are about 1.9 MB per minute of 16 kHz WAV; transcripts are a few KB. When a finished dictation expires, its `audio.wav` is deleted, and the whole folder goes too once it is also outside the newest 200 dictations. Failed dictations expire the same way, but only once they are older than both the setting and 30 days, so they can be retried for at least a month. On top of the setting, all recordings together are held under 1 GB (about nine hours; someone dictating all day records about 30 MB a day): past that, the oldest finished or cancelled dictations lose their `audio.wav` (the text stays), never the newest 10, a failed one, or one still recording or processing. The decision is `HistoryPruning` in the core, shared and tested on both platforms. Expiry runs at launch, after every dictation, when the setting changes, and hourly.

**Export.** History's toolbar exports what the list shows (everything, or what the search found) as CSV, JSON or Markdown (`TypelessCore/HistoryExport.swift`), and a dictation that still has its recording can save a copy of `audio.wav`. The CSV is UTF-8 with a byte-order mark, which Excel needs to show Chinese, quoted per RFC 4180 with CRLF line ends, and a field starting with `=`, `+`, `-`, `@`, a tab or a carriage return gets a leading apostrophe so a spreadsheet shows it as text instead of running it as a formula (OWASP's CSV-injection advice; the JSON is left as it is); its columns and the JSON's keys are `date` (ISO 8601 in the local time it was made, with the offset the current time zone had on that date), `durationSeconds`, `status` (as in `session.json`), `finalText`, `rawText`, `costUSD` and `words`. Markdown has a heading per day and per dictation, the text a paragraph per line (a line that would start a heading, a code fence or an HTML block gets a backslash, so a dictation can't swallow the ones after it), and leaves out dictations without text; dictations stay in History's order, so when they were made in different time zones a day's heading can appear twice. A damaged record can't crash the export: durations and costs are held under a trillion, dates within the years 1 to 9999. Dates and numbers are written by hand (whole seconds cut down, tenths of a second and millionths of a dollar rounded half up) rather than by a formatter, so both apps write the same bytes; `testdata/export-cases.json`, generated by a separate reference implementation, holds the expected files. The snapshot of records is taken on the main thread, the formatting and writing happen off it, and the file is written atomically, so thousands of dictations neither freeze the window nor leave half a file. The approach follows VoiceInk's CSV export, adding the byte-order mark, offsets in the dates, JSON and Markdown.

**Vocabulary files.** The Vocabulary & Style page exports the vocabulary as CSV (`term,heardAs`, the misheard forms of learned terms joined by "; ", for reference; fields protected against formulas as in History's CSV) or as plain text, a term per line, and imports `.csv`, `.tsv` or `.txt` (`TypelessCore/VocabularyTransfer.swift`): UTF-8 with or without a byte-order mark or UTF-16 with one and an even number of bytes (anything else is refused with a hint to save as "CSV UTF-8", rather than guessed and imported garbled); from a CSV or TSV the first column (comma, semicolon or tab, whichever the first line uses most; a `term` / `word` / `phrase` / `vocabulary` / `词` / `词汇` / `术语` header skipped; the export's protecting apostrophe taken off), from text each line, split at commas the way the vocabulary field is, unless the first line holds a tab (Excel's "Unicode Text"), which makes it a table too; trimmed, blank entries skipped, merged without duplicates ignoring case. Only terms are imported, never misheard forms: those make clean-up replace words in every dictation, so they come only from the user's own corrections. Every term goes into every clean-up request, so an import leaves out terms longer than 64 UTF-16 code units (a sentence or a paragraph picked by mistake, not a name) and never takes the vocabulary past 1,000 terms. The app shows how many new terms the file adds (and how many it already has or leaves out, and why) and asks before adding them. Importing is an explicit request for those terms, so a term the user once removed from the learned terms (which would otherwise never be learned again) is taken off that list and added.

## Home page and usage accounting

The Home page (`OpenTypeless/HomePage.swift`, the first sidebar page) shows words dictated, time saved, speaking speed, spend and a daily activity heatmap. The numbers come from `TypelessCore/UsageLedger.swift` and `Usage.swift`, which the Windows app ports line by line; `testdata/usage-cases.json` holds cases both test suites read, so the two apps count and price the same way.

- **Words.** Every Han character and Japanese kana is a word; every run of letters or digits in other scripts is one word, with `'`, `-`, `.`, `,` joining a word only when a letter or digit follows ("don't", "e-mail", "3.5").
- **Time saved** = the time typing the same words would take at the user's typing speed (100 wpm by default, set under General) − the time spent recording (pauses included), never below zero. **Speaking speed** = words ÷ recording minutes.
- **Usage per request.** OpenRouter reports `usage` (tokens, audio seconds and the billed `cost` in USD) with every transcription and in the last chunk of every streamed completion. OpenAI-compatible servers are asked for stream usage with `stream_options.include_usage` (dropped like any other optional parameter if the server rejects it). When a server reports nothing, tokens are estimated from the text (one per CJK character, one per four other characters) and transcription is measured by the chunk's audio length.
- **Cost.** OpenRouter requests count the `cost` OpenRouter reported. Other providers are priced from what the user entered under Models: USD per million input/output tokens for clean-up, USD per minute of audio (or per token when the server counts tokens) for speech-to-text. Requests that can't be priced are counted, and the Home page says how many. Every successful speech-to-text request counts (a retried chunk is billed again), plus the clean-up answer that was kept; the losing request of a hedged clean-up is cancelled after its first tokens and isn't counted.
- **Price list.** `PriceCatalog` reads OpenRouter's public `/models` and `/models?output_modalities=transcription` lists (USD per token, stored per million; negative "varies" prices skipped), cached in `openrouter-prices.json` and refreshed when older than six hours (checked at launch, hourly, and when Home or Models opens). The Models page shows each OpenRouter model's current price.
- **Ledger.** Per-day totals (words, dictations, recording seconds, speech-to-text cost, clean-up cost, unpriced requests) live in `usage.json`, keyed by the local date, so they outlive History's retention and deletions. A dictation's words are added once, when it first finishes (`counted` in `session.json`), dated by when it was recorded; costs are added whenever requests are made, dated today. On the first launch of a version with the ledger it is filled from the dictations History still has.
- **Heatmap.** As many weeks as fit the page width (up to 53), starting on the locale's first weekday; empty days are grey and busy days take one of four shades of the accent colour by quartile of the days shown. Streaks count consecutive days with a dictation, still alive until today ends. Hovering a day shows its date, dictations and words in a bubble at once (system tooltips were too slow to notice on squares this small). On the page, Spend takes a third of the width next to the heatmap's two thirds.
- **Launch.** Opening the app by hand (or again from Finder / the Start menu) shows Home. A launch at login shows nothing unless **Show Home when opened at login** is on (off by default). macOS recognises a login launch from the open-application Apple event, or a launch within two minutes of the Dock starting; Windows from the `--autostart` argument of its Run entry.

## Updates

`TypelessCore/UpdateCheck.swift` reads the repository's GitHub release list (no sign-in; the unauthenticated limit of 60 requests an hour is far above one check a day) and picks the newest published, non-prerelease release that carries this platform's zip. Releases are matched by the zip's file name, `OpenTypeless-<version>-macOS-arm64.zip` (`-macOS-x64.zip` on an Intel Mac, so each Mac stays on a build for its processor), not by tag, so a release may hold one app or both. The disk images next to them are for people; the updater only reads the zips.

`OpenTypeless/Updater.swift` checks 10 s after launch and then whenever 24 h have passed, if **Check automatically** is on (the default); **Check now** is always available. A newer version is downloaded in the background and installed only when the user clicks **Restart to update**, never during a dictation (the click is then held until the dictation finishes). A skipped version isn't offered by automatic checks.

Before anything is replaced:
- The zip's SHA-256 must match the `digest` GitHub publishes for every release file. Without one, the update is offered as a download link only.
- The unpacked app must have our bundle ID and the expected version, and a valid signature (`SecStaticCodeCheckValidity`, strict, nested code).
- If the running copy is signed with a certificate, the new one must satisfy the running copy's designated requirement, i.e. be signed with the same certificate. An ad-hoc copy has nothing to compare against (its requirement is a hash of that exact build).

Install: a helper script started by the app waits for it to quit, moves the old bundle aside, moves the new one into place (putting the old one back if that fails), and opens it. The app notes the version it was installing; if the relaunched app is still older, it says the install failed. When the app can't replace itself (a folder the user can't write to, or macOS running it from an App Translocation path), the update is shown with a link to the release page instead.

Releases are signed in CI with a stable self-signed certificate (`scripts/create-release-cert.sh`, stored as repository secrets), because macOS ties Accessibility and Microphone permission to the signature: with ad-hoc signing every update would ask for them again. Files downloaded by the app itself carry no quarantine flag, so Gatekeeper only warns on the very first manual install.

## UI

- **Menu-bar app** (`LSUIElement`) with a popover. The popover is sized from its SwiftUI content *before* being shown; letting it resize while on screen made it re-anchor off-screen.
- **Settings window:** an `NSSplitViewController` whose sidebar item gets the system Liquid Glass sidebar, with SwiftUI pages. Home comes first and is where the window opens.
- **HUD:** a non-activating, click-through glass capsule that shows recording (level + timer), working, copied, or a short error.
- **Working:** three dots hopping in turn, and a soft accent-coloured bar filling the capsule from the left (`TypelessCore/ProcessingProgress.swift`). Real events move the bar: the speech-to-text chunks still out coming back (up to 45 %), the clean-up's first token (60 %) and its streamed length against the transcript's (up to 95 %), and the paste (full, after which the capsule goes). Without clean-up, speech-to-text takes the bar to 90 %. Between two events the bar creeps at most 70 % of the way to the next one, so a slow request still looks alive without the bar ever getting ahead of the work; it never moves back (a chunk sent again, a second clean-up attempt). A clean-up started ahead of time while the speaker paused streams into the bar only once the dictation takes it over, so one that is dropped never moves it.
- **Localization:** inline `L("中文", "English")` strings, switchable at runtime. The other UI languages (ja, ko, es, pt-BR, fr, de, ru) come from `i18n/strings.json`, keyed by the English text with interpolations numbered `{0}`, `{1}`…, embedded into both apps at build time; a missing translation falls back to English, and `python3 i18n/check.py` (run by CI) finds missing, unused or malformed entries.
